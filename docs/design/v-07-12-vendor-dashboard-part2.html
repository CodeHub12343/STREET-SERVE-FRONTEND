V-03 — the SLA countdown is the vendor's mirror of C-19

  • Each request shows the same 5-minute countdown the customer sees on their Waiting screen (C-19) — from the vendor's side, urgency renders as a shrinking number per row, sorted soonest-to-expire first, so the most time-sensitive request is never buried.
  • A request expiring unanswered (simulate: let Priya S.'s timer hit zero) auto-removes from the inbox exactly as it does on the customer side — one shared server truth, two mirrored UIs.
  • Only Accept/Decline are modeled here; "propose a scheduled stop" (the third FR-2 response) reuses V-07's slot-picking pattern rather than inventing a fourth UI.

V-07 — pending vs. confirmed are visually distinct chips

  • Pending customer-requested bookings (amber) and vendor-confirmed bookings (blue) never share a color — a vendor scanning the week should immediately tell what still needs a response from what's settled.
  • "Propose new time" opens the same slot-picker component the customer uses in C-26 — reused, not rebuilt, so the two sides of one negotiation always show identical available/unavailable times.

V-08 — a real inbox, not a stripped-down chat

  • Two-pane layout (thread list + active conversation) since a vendor may be managing several simultaneous customer questions during a shift — this is the one place the vendor dashboard needs genuine multi-conversation triage, unlike the customer's single-thread-at-a-time C-33.

V-09/V-10 — both explicitly labeled V1.x

  • A visible "V1.x — post-pilot" chip appears at the top of both screens in the mockup itself — these are included in the design system now so the visual language is ready, but the copy is honest that they're not part of the MVP launch, consistent with the Feature Breakdown doc's phasing.
  • V-09's balance/slider directly visualizes the paid-ping fraud-guard rules from Security §4 (rate caps, unique-recipient constraint) via the "14 shares · 3 converted" line — makes the anti-farming reality visible to the vendor funding it, not just an invisible backend rule.

V-11 — benchmarking without shaming

  • Category-average comparison bar sits directly beneath the vendor's own number, same scale, muted color for the benchmark — informative context, not a leaderboard or ranking that could feel punitive to a new vendor still building volume.
  • This is the "vendor analytics benchmarking" item promoted from the Feature Breakdown's Recommended Additions into part of the core V-11 design, since it increases dashboard stickiness at effectively no extra data-collection cost.

V-12 — Stripe owns the compliance surface, this screen just reports it

  • "Manage on Stripe" deep-links to Stripe's own hosted dashboard rather than StreetServe rebuilding bank-detail management — consistent with the Architecture doc's decision not to build a custom ledger/escrow system, this dashboard only visualizes balance and history.

Handoff notes

  • V-03 countdown timers are rendered from a server-supplied expiry timestamp per request (consistent with the server-authoritative timer rule from C-19) — the mockup's local countdown is a simulation stand-in only.
  • V-07 booking state transitions (propose/accept/decline) write to `bookings.status` and are what the customer's C-27 detail screen mirrors — same event, two views.
  • V-09's slider and reload button call `PATCH /ping-budgets/:businessId` and `POST /ping-budgets/:businessId` (API §7).
