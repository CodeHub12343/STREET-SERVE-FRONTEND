Responsive dashboard grid (§2.6i)

  • Full sidebar with labels ≥1280px → icon-only rail 1024–1279px → hidden behind a hamburger <1024px, exactly as specified. Try the width switcher above the browser frame.
  • KPI grids reflow 3→1 column and the order kanban 3→1 column at the same breakpoints — content never gets cramped just because the sidebar collapsed.

V-01 — compliance gate lives in the wizard, not buried later

  • Selecting "Food Truck" immediately surfaces the license requirement inline — direct implementation of the `requires_license`/`regulated_by` category metadata (Database §1) and the launch-category compliance rule (Roadmap Q1). A vendor never discovers this requirement only after trying to go live.

V-02 — the screen a vendor checks constantly

  • Three KPI cards (queue, wave-downs, orders) answer "what needs me right now" before anything else on the page — this is the vendor's home screen, so it leads with action-relevant numbers, not a general dashboard summary.
  • Status toggle uses the same three-state model (Driving/Parked/Away-Closed) as the customer-facing map — one shared vocabulary across both sides of the same feature, not a separate vendor-only status system.
  • Pop-Up Mode is a single, clearly-explained switch, not a status option — matches the Database doc's decision that Pop-Up is an event/flag, not a fourth stored status value.

V-04 — the queue table is server-timestamp truth, read-only on order

  • Position and discount columns are never editable by the vendor — they're a direct read of server-authoritative queue state (FR-3.2), so a vendor can serve out of order operationally but can never manipulate whose discount applies.
  • "Serve" is the only queue action available per row — deliberately narrow, since the discount math and position are enforced server-side regardless of what a vendor clicks.

V-05 — Kanban mirrors `orders.status` exactly

  • Three columns (New/Preparing/Ready) map directly to the order status enum (pending/accepted/ready) plus a completed/cancelled exit — no vendor-invented intermediate states that could drift from what the customer's C-23 tracker shows.
  • Try "Accept" on a New card and "Mark ready" on the Preparing card — both move the count badges live, mirroring exactly what the customer sees on their tracking screen in real time.

V-06 — Today's Special is exclusive, not multi-select

  • Only one item can hold the Today's Special badge at a time (setting a new one should visually imply the old one is replaced) — matches `businesses.today_special_menu_item_id` being a single nullable FK (Database §1), not a list.
  • Availability toggle is separate from the Special flag — an item can be available but not featured, or (rarely) featured while temporarily marked unavailable if it's about to sell out.

Handoff notes

  • V-01's permit upload posts to `license_documents` (Database §1); a vendor cannot toggle to Driving/Parked in V-02 until that row's `status = approved` — enforced server-side per the DB validation rules, matching the client-vs-server enforcement pattern established in the seller screens.
  • V-04/V-05 both subscribe to socket events (`/queue/:queueId`, order status channel) rather than polling — the same real-time backbone the customer-facing C-18–24 screens use, just viewed from the other side of the same events.
