S-07 — My Inventory

  • Deadline chips traffic-light by urgency (green "3 days" → amber "6h" → red overdue) — the same three-color status language as everywhere else in the system, applied to time pressure instead of live/parked/away.
  • Progress bar shows remaining stock at a glance; tapping a card opens quantity/condition detail (not modeled here — reuses S-04's term-card pattern).
  • "Browse nearby inventory" stays present even with active checkouts — a seller isn't blocked from picking up more while something is still out.

S-08 — Log a Sale (FR-8.3)

  • Live gross-total readout as quantity changes, same pattern as S-05's potential-earnings calculator — keeps the number concrete instead of abstract.
  • Oversell guard is a plain-language banner naming the exact held quantity, not a generic "error" — the seller should immediately understand why 5 is blocked when only 4 are checked out, without feeling accused of anything.
  • Manual + photo method exists for cash/off-app sales — still requires proof, consistent with FR-8's chain-of-custody requirement.

S-09 — Return Flow

  • Reconciliation card does the arithmetic for the seller (checked out − sold = returning) rather than asking them to self-report a returning count — removes an entire class of honest mistakes.
  • "✓ Accounts for all 6" is the reassurance state; a mismatch (simulate below) replaces it with a specific correction prompt rather than a blocking dead-end.
  • Scan uses the same camera-viewfinder metaphor as S-06's pickup checkout — one learned interaction for both check-out and check-in.

S-10 — Settlement

  • Net payout leads, in the same "big green number" treatment used for savings elsewhere in the app — the settlement is framed as an earning, not an accounting statement.
  • Full split (gross → platform fee → hub share → net) itemized directly here, unhidden — sellers see exactly where every dollar of their own consignment went, distinct from the customer receipt's collapsed disclosure (C-24), because this is the seller's business record, not incidental trivia.
  • Trust Score shown as a ring + explicit delta reason ("+3 · on-time return") — never a bare number, per FR-10.1's explainability requirement.

Handoff notes

  • S-08's confirm action calls `POST /checkouts/:id/sales`; server rejects any quantity exceeding the checkout's remaining balance regardless of client-side guard (API §9, DB validation rules) — the UI block is a UX courtesy, not the actual enforcement boundary.
  • S-09 return writes `inventory_returns` + triggers `settlements` computation (Database §3); the reconcile numbers shown are read from the same aggregate the server uses, so they can never drift from what actually gets billed.
